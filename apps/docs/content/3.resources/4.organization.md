## Choose stable URIs

Use a scheme that describes the application's content: `docs://guides/installation`, `projects://123/summary`, or an application HTTPS URI. A resource URI is a public identifier, so avoid putting credentials or private filesystem details in it.

## Label a catalog

```ts [server/mcp/resources/help.ts]
import { defineMcpResource } from '@nuxtjs/mcp-toolkit/server'

export default defineMcpResource({
  uri: 'docs://help',
  description: 'How to use this MCP server',
  group: 'documentation',
  tags: ['readonly', 'help'],
  mimeType: 'text/plain',
  handler: () => 'Use the greet tool to greet someone by name.',
})
```

Subdirectories infer groups; explicit `group` wins. Groups and tags describe metadata and do not grant access. Their behavior matches [tools](/tools/groups-organization#groups-and-tags).

## Separate endpoint ownership

Use `mcp.servers` to give public and private definitions different roots. A definition belongs only to an endpoint that scans its directory. Nuxt layers overlay the same relative path in priority order; duplicate identities from different files remain errors.

Add `scopes` to require verified token scopes for reads and application enumeration/completion callbacks. The static metadata remains listed after endpoint authentication. If the catalog itself is sensitive, use a separately authenticated endpoint.

The beta removes per-resource `enabled()` guards. Read authorization from the current request, rather than changing a shared catalog per user. See [endpoint organization](/handlers/organization), [OAuth](/getting-started/oauth), and [catalog queries](/advanced/listing-definitions).
