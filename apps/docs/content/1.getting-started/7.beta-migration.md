Nuxt MCP Toolkit 1.0 uses `nitro-mcp-toolkit` and h3-mcp for protocol handling. Nuxt supplies discovery, layers, auto-imports, and development tooling. Requires Nuxt 4.6 or later.

## What changes and why

Creating a tool still means default-exporting `defineMcpTool()` from `server/mcp/tools`. Nuxt discovers the file and infers its name. Input types come from the schema, output data can be returned directly, and tools without arguments need no input schema. The helpers provide contextual types; no `satisfies` check or manual callback types are required for ordinary definitions.

| Change | Reason |
| --- | --- |
| One shared Nitro runtime | Nuxt and standalone Nitro use the same protocol implementation and revision compatibility |
| Complete schemas such as `z.object(...)` | The shared API accepts supported Standard Schema libraries instead of depending on Zod shapes |
| Named endpoints in `mcp.servers` | Each endpoint discovers its own directories, keeping public and private catalogs separate |
| Runtime auth-file references | Authentication callbacks can read deployment secrets without manual tool registration or embedding secrets in build-time options |
| Explicit request events | Shared definitions read the current caller and request context on every invocation |
| Nitro application caching | Applications control storage, lifetime, and identity-aware keys; the old per-tool shortcut is removed |

These include toolkit design choices as well as protocol changes. Convenience helpers are not inherently incompatible with MCP. Schema examples are JSON Schema annotations, while `_meta.inputExamples` remains a custom client convention. Application caching is also separate from the protocol's client cache hints.

## Schemas and callbacks

Wrap raw Zod shapes with `z.object(...)`. Use a supported complete Standard Schema implementation. With an input schema, callbacks receive `(args, event)`; without one, they receive `event`.

```diff
-inputSchema: { id: z.string() },
-handler: (args, extra) => ...,
+inputSchema: z.object({ id: z.string() }),
+handler: (args, event) => ...,
```

`event.context.mcp` exposes protocol context, request cancellation, progress, and logging. Broadcast catalog changes with `event.context.mcp.notifier.toolsChanged()`; `notify` remains the engine's request notification function. Read identity from verified request context rather than capturing it in a shared definition.

A tool with `outputSchema` returns its schema data directly. Use `toolResult(...)` for an explicit protocol envelope, including an `isError` result. Plain objects always mean schema data when an output schema is present.

## Endpoints

Replace `defineMcpHandler` configuration files with named servers in `mcp.servers`:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxtjs/mcp-toolkit'],
  mcp: {
    servers: {
      default: { dir: 'mcp' },
      admin: {
        dir: 'mcp-admin',
        auth: './server/mcp-admin/auth.ts',
      },
    },
  },
})
```

Move `server/mcp/handlers/admin/{tools,resources,prompts}` into `server/mcp-admin/{tools,resources,prompts}`. Remove the old `index.ts` handler configuration files. Every endpoint discovers only its own roots; `defaultHandlerStrategy` and global handler-attribution filters are removed.

For live authentication, reference a file default-exporting `defineMcpAuth({ validate })` options; see [runtime authentication](https://mcp-toolkit.nuxt.dev/getting-started/configuration#read-authentication-at-runtime). Other callbacks or explicit definition collections can use `createMcpHandler(...)` in a normal Nuxt route. Native Nuxt middleware runs before the engine and its context reaches definitions.

## Resources and prompts

Use `uriTemplate` instead of an SDK `ResourceTemplate`. Template `list` returns descriptors directly. Resource `mimeType`, `icons`, and `_meta` are top-level fields. Replace the `file` shorthand with an explicit URI and handler or a Nitro server asset.

Prompt strings become user messages. Return an explicit `messages` result for an assistant role. Replace `completable()` with an `arguments` entry carrying a completion callback.

## Authorization and catalogs

`enabled(event)` is removed. Put sensitive catalogs on separately authenticated endpoints. Use verified OAuth claims and definition `scopes` to authorize invocation, enumeration, and completion. Static metadata stays listed when only scopes are required.

Import a generated server from `nitro-mcp-toolkit/servers` and read its `definitions` array. Filter summaries with ordinary array operations. The `listMcp*` and `getMcp*` query helpers are removed. `X-MCP-Tools` still narrows a client's tool selection and never grants access.

Configure JWT resource-server support through `mcp.oauth` or each named endpoint. The module mounts protected-resource metadata and verifies resource-bound access tokens. Provider login and token issuance remain with the authorization server. See [OAuth setup](/getting-started/oauth).

## State and client compatibility

Use `session: true` for legacy engine sessions. Modern clients use request context and continuations. Store durable application state by verified user or tenant identity, independently of a particular MCP connection. The old session-storage helpers are removed.

The default `era: 'dual'` supports modern and 2025 Streamable HTTP clients. Ordinary tools, resources, and prompts work in both modes. Input-required continuations require modern capabilities; expose ordinary arguments or instructions for older clients. Do not assume every client supports interactive requests.

The toolkit delegates continuation helpers to h3-mcp. Use `defineRequestState` for signed state, validate resumed input, and reauthorize the operation. Signed state is visible to its holder and is not automatically single-use.

## Keep output schemas and move caching to services

`outputSchema` remains supported, with return-type inference and runtime validation. Use a complete schema such as `z.object({ total: z.number() })` and return its data directly. No-argument tools omit `inputSchema` rather than adding `z.object({})`.

Replace per-tool `cache: '10m'` with a Nitro cached application function using `maxAge: 600` seconds and an explicit `swr` setting. Keep that function outside the handler; check current authorization before calling it, and include verified identity in the key for private data. See the [complete cached product example](/tools/errors-caching#cache-the-data-used-by-a-tool).

JSON Schema’s `examples` annotation can describe expected inputs. Zod 4 emits it from `.meta({ examples })`. See [annotations and metadata](/tools/annotations) for the distinction between schema examples, custom `_meta.inputExamples`, and MCP metadata.

## Removed runtime helpers

- Code Mode and `experimental_codeMode`; remove `secure-exec` when no other feature needs it.
- `useMcpServer`, `getSdkServer`, direct SDK registration, and SDK callback-extra types.
- `useMcpSession` and `invalidateMcpSession`; use explicit application storage.
- `useMcpElicitation`; use the engine's input-request helpers with capability checks.
- `useMcpLogger`; use `event.context.mcp.log` for client logging and an application logger for server diagnostics.
- `mcp:server:created`, `mcp:config:resolved`, and `mcp:definitions:paths`.
- Per-definition `cache: '5m'`; cache application services with Nitro utilities.

`mcp:tool:called` remains available for configured endpoints. A listener error reaches the caller. Keep server diagnostics in application logging; protocol Logging is deprecated. The old typed `inputExamples` helper is not currently available. Use schema examples for general documentation, or `_meta.inputExamples` only for a client integration that expects that custom convention; it is not a standard MCP input-example field.

## MCP Apps are deferred

The 1.0 beta focuses on tools, resources, prompts, authentication, streaming, and MCP client compatibility. Built-in MCP Apps support is deferred.

The beta removes:

- `defineMcpApp` and the `McpApp*` types.
- `useMcpApp` and the `@nuxtjs/mcp-toolkit/app` entrypoint.
- `mcp.apps` and `mcp.appsDir` configuration.
- Automatic discovery of `app/mcp/*.vue`, Vue widget bundling, and host-bridge composables.

Files under `app/mcp` no longer generate tools or `ui://mcp-app/*` resources. Remove configuration and imports for the built-in integration.

## Move handlers into tools

Move the server-side logic from each `defineMcpApp` handler into a file under `server/mcp/tools`. The tool returns ordinary MCP data:

```ts [server/mcp/tools/status.ts]
import { defineMcpTool } from '@nuxtjs/mcp-toolkit/server'

export default defineMcpTool({
  description: 'Read the current status',
  handler: async () => ({ status: 'ready' }),
})
```

The client can call `status` as a regular tool. The beta does not generate or render a Vue widget for its result.

General resources and custom metadata remain available. Apps may return as a separately reviewed integration. Applications that require the existing built-in widget integration can remain on the 0.x release while testing the beta separately.

## Verify your migrated application

Run Nuxt preparation and your type checker, then test the built application with modern and legacy clients. Include scopes, private ownership, wrong/expired tokens, resource enumeration, prompt completion, streaming disconnects, and interaction capability fallbacks. See [testing](/advanced/evals).
