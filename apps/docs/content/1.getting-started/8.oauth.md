## Connect an authorization provider

The toolkit acts as the OAuth **resource server**. Your authorization provider handles login, client registration, consent, and access-token issuance. MCP clients discover that provider through the endpoint's protected-resource metadata. See the [MCP authorization model](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

Configure the provider to issue access tokens for the MCP resource URL. Browser session cookies and tokens issued for another API are not interchangeable with those tokens.

## Configure OAuth at runtime

Keep Nuxt configuration focused on endpoint discovery:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxtjs/mcp-toolkit'],
  mcp: {
    servers: {
      default: { dir: 'mcp' },
    },
  },
})
```

Put OAuth configuration beside the definitions in `server/mcp/index.ts`. Replace the resource, issuer, and JWKS URLs with your deployed endpoints:

```ts [server/mcp/index.ts]
import { createMcpOAuth, defineMcpServer } from '@nuxtjs/mcp-toolkit/server'

export default defineMcpServer({
  oauth: createMcpOAuth({
    resource: 'https://example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    jwt: { jwks: 'https://auth.example.com/.well-known/jwks.json' },
    scopesSupported: ['profile:read'],
  }),
})
```

`createMcpOAuth` prepares verification and discovery. Pass that prepared instance to `defineMcpServer`, or use a provider connector that returns one; see [provider connectors](#use-provider-connectors).

The generated module mounts RFC 9728 metadata at `/.well-known/oauth-protected-resource/mcp` for this resource. Missing or invalid credentials return HTTP 401 with a `WWW-Authenticate` challenge pointing to that metadata. A public endpoint's metadata route returns 404. Use the public endpoint URL without a trailing slash consistently in `resource`, provider configuration, and the token audience.

JWT verification checks the signature, issuer, resource audience, expiry, and a nonempty subject. Issuer defaults to `authorizationServers`; audience defaults to `resource`. An `authorizedParties` allowlist adds a client check and does not replace audience validation. For providers using a specific access-token profile, `jwt.typ` requires a protected-header type and `jwt.requiredClaims` adds required claims.

Configuration and verification callbacks in `index.ts` run on the server at runtime. No OAuth credentials or callbacks need to go in `nuxt.config.ts`. Resource, issuer, and JWKS URLs are public configuration; keep any verifier credentials in private runtime configuration. The toolkit does not issue access tokens. `auth` and `oauth` cannot coexist on the same server, and runtime authentication cannot be combined with authentication configured in module options.

Runtime OAuth uses discovery at the authorization server's issuer. It does not mount a root `/.well-known/oauth-authorization-server` compatibility proxy; the existing static module configuration retains that proxy behavior when configured.

## Authorize a verified identity

Use `authorize` for an endpoint-wide policy after token verification. For example, with a provider that includes a verified `org_id` claim:

```ts [server/mcp/index.ts]
import { defineMcpServer } from '@nuxtjs/mcp-toolkit/server'
import { clerk } from '@nuxtjs/mcp-toolkit/oauth/clerk'

export default defineMcpServer({
  oauth: clerk({ resource: 'https://example.com/mcp' }),
  authorize: async (identity) => identity.org_id === 'org_example',
})
```

The callback receives `(identity, event)`, where `identity.sub` is a required, verified subject and `event` is the current MCP request. Other claims depend on the verifier and provider. Replace this sample organization check with your application's membership or access policy; asynchronous database checks belong here.

Returning `false` denies a verified identity with HTTP 403 and no authentication challenge. Missing or invalid tokens return HTTP 401 before `authorize` runs. `authorize` requires OAuth; it does not replace token verification or per-definition scope checks. Verified claims remain available at `event.context.oauth`.

When neither the endpoint nor the application uses OAuth/JWT helpers, Nitro production builds omit the toolkit's unused `jose` files. `jose` remains an installed package dependency for JWT verification; tree-shaking reduces deployment output, not the installed dependency list.

## Require scopes on definitions

```ts [server/mcp/tools/whoami.ts]
import { z } from 'zod'
import { defineMcpTool } from '@nuxtjs/mcp-toolkit/server'

export default defineMcpTool({
  description: 'Read the verified user identifier',
  scopes: ['profile:read'],
  annotations: { readOnlyHint: true, openWorldHint: false },
  outputSchema: z.object({ userId: z.string() }),
  handler: (event) => {
    const userId = event.context.oauth?.sub
    if (!userId) throw new Error('A verified user is required.')
    return { userId }
  },
})
```

`scopesSupported` advertises available scopes; `scopes` requires every named scope on each invocation. Scope claims come from verified `scope` or `scp`. Checks also protect resource-template enumeration and resource/prompt completion callbacks.

Scoped definitions still appear in the authenticated catalog. Protect an endpoint separately when its metadata is sensitive. Authentication and authorization run for the current request; application queries must also enforce ownership and tenant boundaries.

## Configure OAuth per endpoint

Each discovered directory can have its own runtime `index.ts`:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxtjs/mcp-toolkit'],
  mcp: {
    servers: {
      default: { dir: 'mcp' },
      admin: { dir: 'mcp-admin' },
    },
  },
})
```

```ts [server/mcp-admin/index.ts]
import { createMcpOAuth, defineMcpServer } from '@nuxtjs/mcp-toolkit/server'

export default defineMcpServer({
  oauth: createMcpOAuth({
    resource: 'https://example.com/mcp/admin',
    authorizationServers: ['https://auth.example.com'],
    jwt: { jwks: 'https://auth.example.com/.well-known/jwks.json' },
    scopesSupported: ['admin:read'],
  }),
})
```

The admin resource has its own metadata path, `/.well-known/oauth-protected-resource/mcp/admin`. Configure the provider's resource indicator and token audience for that exact resource. Authentication in `server/mcp/index.ts` protects the default endpoint; configure each additional endpoint separately.

### Existing static configuration

Serializable JWT configuration in `mcp.oauth` or `mcp.servers.<name>.oauth` remains supported:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxtjs/mcp-toolkit'],
  mcp: {
    oauth: {
      resource: 'https://example.com/mcp',
      authorizationServers: ['https://auth.example.com'],
      jwt: { jwks: 'https://auth.example.com/.well-known/jwks.json' },
      scopesSupported: ['profile:read'],
    },
  },
})
```

Choose one place for authentication on each endpoint. Use runtime `index.ts` for callbacks, an existing provider client, or `authorize`.

## Use provider connectors

Connectors return prepared OAuth instances for `defineMcpServer`. Provider login, client registration, consent, token issuance, and refresh still need provider-side setup.

### Clerk

```ts [server/mcp/index.ts]
import { defineMcpServer } from '@nuxtjs/mcp-toolkit/server'
import { clerk } from '@nuxtjs/mcp-toolkit/oauth/clerk'

export default defineMcpServer({
  oauth: clerk({ resource: 'https://example.com/mcp' }),
})
```

Clerk reads `CLERK_PUBLISHABLE_KEY` or `NUXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, or accepts `publishableKey` explicitly. This form verifies JWTs using Clerk's JWKS. Configure resource-bound access tokens with `aud` matching the MCP resource. A client `azp` allowlist does not replace that requirement.

For Clerk OAuth access tokens that may be opaque or JWTs, pass an existing `@clerk/backend` client through `client`. The SDK-backed form requires `@clerk/backend` 3.27.0 or later for OAuth audience validation:

```ts [server/mcp/index.ts]
import { createClerkClient } from '@clerk/backend'
import { defineMcpServer } from '@nuxtjs/mcp-toolkit/server'
import { clerk } from '@nuxtjs/mcp-toolkit/oauth/clerk'

const client = createClerkClient({
  secretKey: process.env.CLERK_SECRET_KEY,
})

export default defineMcpServer({
  oauth: clerk({ resource: 'https://example.com/mcp', client }),
})
```

Configure `CLERK_SECRET_KEY` and the publishable key at runtime, or reuse your application's initialized backend client. Only OAuth access tokens for the configured resource are accepted; Clerk session tokens and browser cookies do not authorize this endpoint. This form exposes the verified subject, issuer, audience, client ID, and scopes through `event.context.oauth`; it does not copy arbitrary JWT claims such as `org_id`. Use `identity.sub` for application membership checks. If `authorizedParties` is set, opaque tokens are refused because the SDK's opaque-token result does not expose `azp`.

### Okta

```ts [server/mcp/index.ts]
import { defineMcpServer } from '@nuxtjs/mcp-toolkit/server'
import { okta } from '@nuxtjs/mcp-toolkit/oauth/okta'

export default defineMcpServer({
  oauth: okta({ resource: 'https://example.com/mcp', domain: 'acme.okta.com' }),
})
```

Okta uses a custom authorization server. Pass `issuer` instead of `domain` for a full custom-server URL. Org-server opaque tokens require a custom resource verifier.

### WorkOS

```ts [server/mcp/index.ts]
import { defineMcpServer } from '@nuxtjs/mcp-toolkit/server'
import { workos } from '@nuxtjs/mcp-toolkit/oauth/workos'

export default defineMcpServer({
  oauth: workos({
    resource: 'https://example.com/mcp',
    issuer: 'https://acme.authkit.app',
  }),
})
```

WorkOS uses Connect access tokens with the MCP resource configured as a Resource Indicator. `WORKOS_AUTHKIT_ISSUER` can supply the issuer. AuthKit session tokens or tokens whose audience is only the environment client ID are refused.

### Better Auth

```ts [server/mcp/index.ts]
import { defineMcpServer } from '@nuxtjs/mcp-toolkit/server'
import { betterAuth } from '@nuxtjs/mcp-toolkit/oauth/better-auth'

export default defineMcpServer({
  oauth: betterAuth({
    resource: 'https://example.com/mcp',
    issuer: 'https://auth.example.com/api/auth',
    jwks: 'https://auth.example.com/api/auth/jwks',
    scopesSupported: ['profile:read'],
  }),
})
```

The optional adapter uses Better Auth's official `verifyBearerToken` from `better-auth/oauth2` and requires `better-auth` version 1.7.16 or later within 1.x (`^1.7.16`). Supply the exact issuer and JWKS URL, including the provider's auth base path; the resource URL is the expected token audience. Verification requires the `at+jwt` access-token type, expiry, a nonempty subject, and a nonempty `azp`. Verified claims populate `event.context.oauth`.

This adapter verifies JWT OAuth access tokens only. It has no auth-instance overload or opaque-token introspection, and does not check live session revocation: a locally verified JWT can remain valid until expiry. Session JWTs, opaque tokens, and proof-bound tokens are refused. DPoP is unsupported.

Your application must still configure [Better Auth's OAuth provider plugin](https://www.better-auth.com/docs/plugins/oauth-provider), its resources and scopes, login and consent pages, client registration, and the plugin's database schema or migrations. The toolkit adds no database or provider tables. A Better Auth login session alone does not issue an MCP access token. See the provider's [resource-server guide](https://www.better-auth.com/docs/plugins/oauth-provider/resource-server) for the distinction between session tokens and OAuth access tokens. Provider support for DPoP does not enable DPoP in the toolkit.

## Use a request-aware verifier

`createMcpOAuth` also accepts `verify(token, event)` for opaque tokens or provider-specific verification. The callback must validate the token for this resource, set verified claims on `event.context.oauth`, and return a boolean. Set a nonempty `sub` when using `authorize`; set verified `scope` or `scp` claims when requiring scopes. Never treat decoding a JWT or reading a session cookie as token verification.

When both `jwt` and `verify` are configured, JWT verification runs first. Disabling audience validation with `jwt.audience: false` requires a custom `verify` callback that validates resource binding. Runtime configuration still gets automatic protected-resource metadata mounting.

DPoP is unsupported. Proof-bound access tokens are rejected rather than accepted as ordinary bearer tokens; JWT verification rejects tokens carrying a `cnf` claim. A custom verifier must enforce the same bearer-only boundary.

For explicit definition collections or custom routing, see the [manual OAuth wiring example](/examples/authentication#compose-oauth-manually). Manual composition owns metadata mounting.

## Verify the deployed flow

Check unauthenticated rejection and the metadata URL, valid tokens, wrong audience/issuer, expired tokens, denied endpoint authorization, missing scopes, proof-bound tokens, and separate users. Then test the real provider login and refresh flow with each intended client. Local JWT verification does not prove provider login or universal client compatibility.

See [authentication examples](/examples/authentication) and [testing](/advanced/evals).
