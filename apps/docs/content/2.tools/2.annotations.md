## Describe tool behavior

Annotations help clients present a tool and decide how to ask their user for confirmation. They are hints, not permission checks.

```ts [server/mcp/tools/calculate-total.ts]
import { z } from 'zod'
import { defineMcpTool } from '@nuxtjs/mcp-toolkit/server'

export default defineMcpTool({
  description: 'Add a list of numbers',
  annotations: {
    readOnlyHint: true,
    openWorldHint: false,
  },
  inputSchema: z.object({ values: z.array(z.number()) }),
  outputSchema: z.object({ total: z.number() }),
  handler: ({ values }) => ({ total: values.reduce((sum, value) => sum + value, 0) }),
})
```

| Annotation | Default | Meaning |
| --- | --- | --- |
| `readOnlyHint` | `false` | The tool does not modify its environment when `true` |
| `destructiveHint` | `true` | A modifying tool may perform destructive updates |
| `idempotentHint` | `false` | Repeating a modifying operation has no additional effect |
| `openWorldHint` | `true` | The tool may interact with external entities |

`destructiveHint` and `idempotentHint` apply to modifying tools. Choose them based on the operation; an increment operation and a set operation have different retry behavior. Authenticate and authorize the real operation regardless of these hints. See the [MCP tool annotations specification](https://modelcontextprotocol.io/specification/2026-07-28/schema#toolannotations).

## Add examples to a schema

[JSON Schema](https://json-schema.org/understanding-json-schema/reference/annotations) defines an `examples` annotation. [Zod 4](https://zod.dev/metadata) can emit it from schema metadata:

```ts [server/mcp/tools/preview-search.ts]
import { z } from 'zod'
import { defineMcpTool } from '@nuxtjs/mcp-toolkit/server'

const searchInput = z.object({
  query: z.string().min(1).describe('Search terms'),
  limit: z.number().int().min(1).max(50).default(10),
})

const examples = [
  { query: 'caching' },
  { query: 'output schemas', limit: 5 },
] satisfies z.input<typeof searchInput>[]

export default defineMcpTool({
  description: 'Preview validated search parameters',
  inputSchema: searchInput.meta({ examples }),
  handler: args => args,
})
```

The `satisfies` check keeps the examples compatible with the input type, including fields with defaults. It does not replace runtime validation of actual calls. Clients may use schema examples, but their presence does not guarantee that a host shows them or passes them to a model.

`.meta(...)` here is Zod's schema API. It produces JSON Schema annotations; it is separate from a tool's MCP `_meta` field.

## Use `_meta` for extension metadata

`_meta` is a standard MCP field for additional metadata. The meanings of its entries depend on the protocol or extension defining each key. Use a vendor namespace for your own integration:

```ts [server/mcp/tools/ping.ts]
import { defineMcpTool } from '@nuxtjs/mcp-toolkit/server'

export default defineMcpTool({
  description: 'Check connectivity',
  _meta: { 'com.example/documentationUrl': 'https://example.com/mcp/ping' },
  handler: () => 'pong',
})
```

A client without support for that key can ignore it. The toolkit handles reserved request metadata, such as protocol version and capabilities; you do not add those fields to every tool definition. See the [MCP metadata rules](https://modelcontextprotocol.io/specification/2026-07-28/basic#meta).

### Migrate the old `inputExamples` helper

The beta currently does not accept the 0.x top-level `inputExamples` property. The old helper serialized its values into `_meta.inputExamples`; moving them there preserves that custom convention, not a standard core MCP feature:

```ts [server/mcp/tools/preview-search.ts]
import { z } from 'zod'
import { defineMcpTool } from '@nuxtjs/mcp-toolkit/server'

const searchInput = z.object({ query: z.string() })
const examples = [{ query: 'caching' }] satisfies z.input<typeof searchInput>[]

export default defineMcpTool({
  description: 'Preview search parameters for a client using inputExamples metadata',
  inputSchema: searchInput,
  _meta: { inputExamples: examples },
  handler: args => args,
})
```

Only use that convention when a client integration expects it. `_meta` is an open metadata object and does not infer the example type; the explicit `satisfies` check supplies that check here. For general schema documentation, prefer the schema's `examples` annotation.

Groups, tags, and scopes also have typed toolkit properties. Use those properties rather than constructing their generated `_meta` entries by hand.
