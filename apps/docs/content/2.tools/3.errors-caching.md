## Report execution failures

Throw an application error when a valid tool call cannot be completed. The toolkit converts it to an `isError` result:

```ts [server/mcp/tools/divide.ts]
import { z } from 'zod'
import { defineMcpTool } from '@nuxtjs/mcp-toolkit/server'

export default defineMcpTool({
  description: 'Divide one number by another',
  inputSchema: z.object({ numerator: z.number(), denominator: z.number() }),
  outputSchema: z.object({ quotient: z.number() }),
  handler: ({ numerator, denominator }) => {
    if (denominator === 0) throw new Error('The denominator must not be zero.')
    return { quotient: numerator / denominator }
  },
})
```

The error result contains a text block and `isError: true`. The client can show that message to the user or let the model correct its request.

For an HTTP-style application error in Nuxt, import `createError` from `nuxt/server`. Numeric `status`/`statusCode` values and attached `data` are preserved in the tool error text. Keep public messages appropriate for callers; use your application logger for private diagnostics.

An unknown tool, invalid arguments, or an output that violates `outputSchema` is a protocol error rather than a successful tool result. Resources and prompts have no tool-style `isError` envelope.

## Cache the data used by a tool

Use Nitro's `defineCachedFunction` around reusable application work. Keep the cached function outside the handler so requests share it. A cache hit still passes through the MCP engine's invocation checks and output validation.

The following example targets Nuxt 4 with Nitro 2 on Node. Replace the example product service URL with your own upstream:

```ts [server/mcp/tools/get-product.ts]
import { defineCachedFunction } from 'nitropack/runtime'
import { defineMcpTool } from '@nuxtjs/mcp-toolkit/server'
import { z } from 'zod'

const productSchema = z.object({
  id: z.string(),
  name: z.string(),
})

const getProduct = defineCachedFunction(async (id: string) => {
  const response = await fetch(
    `https://api.example.com/products/${encodeURIComponent(id)}`,
  )
  if (!response.ok) throw new Error('The product service is unavailable.')
  return productSchema.parse(await response.json())
}, {
  name: 'mcp-public-product',
  maxAge: 600,
  swr: false,
})

export default defineMcpTool({
  description: 'Get a public product',
  annotations: { readOnlyHint: true, openWorldHint: true },
  inputSchema: z.object({ id: z.string().min(1) }),
  outputSchema: productSchema,
  handler: ({ id }) => getProduct(id),
})
```

The function arguments form the default cache key, so different product IDs use different entries. Upstream data is parsed before it is cached, and `outputSchema` still validates what the MCP client receives. The handler returns ordinary data, not a cached JSON-RPC response.

`maxAge: 600` means ten minutes; Nitro cache lifetimes are measured in seconds. With `swr: false`, an expired entry waits for fresh data. Use `swr: true` when serving stale data while refreshing is acceptable. Set the value explicitly rather than relying on version-specific defaults.

The 0.x tool option `cache: '10m'` is not accepted by the beta. This is the current replacement; it does not require changes to the tool's output schema.

## Use the import for your Nitro version

| Host | Cached-function import | Tool-helper import |
| --- | --- | --- |
| Nuxt 4 / Nitro 2 | `nitropack/runtime` | `@nuxtjs/mcp-toolkit/server` |
| Standalone Nitro 3 | `nitro/cache` | `nitro-mcp-toolkit` |

The same cached-function pattern works with the relevant host import. See the [Nitro 2 cache guide](https://v2.nitro.build/guide/cache#cached-functions) and [Nitro 3 cache guide](https://nitro.build/docs/cache#cached-functions) for storage and invalidation APIs for your installed release.

On workers, cache persistence and background refresh also depend on the host's storage and request lifecycle. Follow that Nitro version's lifecycle guidance. In a Nitro 2 host, the toolkit's H3 v2 MCP event is not the native H3 v1 cache event; passing it as the first argument is not a verified replacement for the host lifecycle integration.

## Keep identity and authorization explicit

For private data, read the verified user or tenant from the current request. Check access on every invocation, then pass that identity and all data-selection arguments into the cached application function. Those values must participate in its key.

For example, a cached function taking `(userId, projectId)` separates users' project data through the default argument hash. If it takes only `projectId` while reading the user from a closure, its cache cannot distinguish those users. Do not move the authorization check inside a function that can return from cache without running it.

Cache plain, serializable application values. Perform mutations outside the cache and invalidate affected entries through the storage or invalidation API supported by your installed Nitro version.

## Configure storage when sharing instances

Nuxt 4 / Nitro 2 uses the `cache` storage mount. Configure it when multiple instances need a shared cache:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitro: {
    storage: {
      cache: { driver: 'redis', url: process.env.REDIS_URL },
    },
  },
})
```

Choose the storage configuration for your deployment and Nitro version. An in-process cache is not shared between server instances or preserved across restarts. Nitro 3 storage configuration can differ from the Nitro 2 example above.

## Distinguish server caching from MCP cache hints

| Mechanism | What it controls |
| --- | --- |
| Nitro cached functions | Reuse of application work on the server |
| MCP `ttlMs` (milliseconds) / `cacheScope` | How clients or intermediaries may reuse eligible protocol results |

MCP client cache hints do not cache your handler's execution. They are also separate from `outputSchema`, which describes and validates returned data. See the [MCP tool protocol](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) for cacheable listing results.
