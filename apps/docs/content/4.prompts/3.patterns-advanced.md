## Keep prompts focused

A prompt should establish a useful task: review code, explain a document, plan a migration, or summarize supplied content. Make its arguments and expected outcome explicit. A prompt prepares a conversation; a tool performs an operation.

```ts [server/mcp/prompts/engineering/review-code.ts]
import { z } from 'zod'
import { defineMcpPrompt } from '@nuxtjs/mcp-toolkit/server'

export default defineMcpPrompt({
  description: 'Review code for correctness and maintainability',
  group: 'engineering',
  tags: ['review', 'readonly'],
  inputSchema: z.object({
    code: z.string().min(1).describe('Code to review'),
    focus: z.enum(['correctness', 'performance', 'security']).default('correctness'),
  }),
  handler: ({ code, focus }) => `Review this code for ${focus}:\n\n${code}`,
})
```

## Treat supplied content as content

When embedding a document, code sample, or third-party text, tell the model what to do with it. Do not imply that untrusted source content is a new instruction from the user. Avoid including secrets in a prompt because its messages may be sent to the client's model provider.

## Authorize current requests

Use endpoint authentication for private catalogs and definition `scopes` for expansion and completion. Scope checks happen on each invocation. Static prompt metadata remains listed after endpoint authentication; groups and tags do not hide it.

The beta removes `enabled(event)` and session-bound prompt mutation. Use explicit endpoint ownership and request-specific data in handlers instead. See [catalog authorization](/advanced/dynamic-definitions) and [OAuth](/getting-started/oauth).

## Verify the expansion

Test argument defaults, rejected values, and message roles with a real MCP client before running model evals. A deterministic prompt result test catches contract problems without depending on a model. See [testing and evals](/advanced/evals) and [prompt examples](/examples/prompt-examples).
