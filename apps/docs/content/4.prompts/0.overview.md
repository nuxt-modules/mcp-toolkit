## Publish a conversation template

Prompts give a client reusable instructions and context. They do not execute a model themselves. The host decides how to present and expand them, so avoid assuming a particular IDE menu or slash-command interface.

Create one default export per file under `server/mcp/prompts`:

```ts [server/mcp/prompts/review-code.ts]
import { z } from 'zod'
import { defineMcpPrompt } from '@nuxtjs/mcp-toolkit/server'

export default defineMcpPrompt({
  description: 'Review code for correctness and maintainability',
  inputSchema: z.object({
    code: z.string().min(1).describe('Code to review'),
    focus: z.enum(['correctness', 'performance', 'security']).default('correctness'),
  }),
  handler: ({ code, focus }) => `Review this code for ${focus}:\n\n${code}`,
})
```

The filename becomes `review-code`. The input schema parses the arguments and applies the default focus. A string return becomes one **user** message.

## Choose the result you need

Return a string for a single user message or an explicit `{ messages }` result for a conversation with user and assistant messages. There is no definition-level `role` option.

A no-argument prompt omits `inputSchema`. Use the explicit `arguments` list when a field needs a completion callback. Prompt arguments arrive through MCP as strings; use string schemas and validate or transform their values deliberately.

Use groups and tags to organize prompts, and `scopes` to gate expansion and completion. Put sensitive catalog metadata behind endpoint authentication.
