## Choose a root relative to server directories

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxtjs/mcp-toolkit'],
  mcp: { dir: 'assistant' },
})
```

The module scans `server/assistant/{tools,resources,prompts}` in the app and its extended Nuxt layers. Do not include `server/` in a Nuxt-relative `dir`. Standalone Nitro's module uses paths relative to its root instead.

## Overlay multiple roots

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxtjs/mcp-toolkit'],
  mcp: { dir: ['assistant-overrides', 'assistant'] },
})
```

The first root containing a relative file wins; within each root the app precedes extended layers. This supports overriding one tool while retaining the rest of a layer. Different relative files with duplicate advertised names still fail validation.

Use `mcp.servers` when directories belong to distinct endpoints. Keep manually composed shared definitions outside scanned roots unless they should also be registered automatically.

## Verify discovery

Read the endpoint report during the build. It names the served roots and counts definitions, and warns about empty or near-miss directories. Inspect `handler.definitions` for the same runtime catalog.

The old `mcp:definitions:paths` hook is removed. Configure directory arrays and Nuxt layers explicitly. Framework authors can use the standalone Nitro module's generated `include` contract; the Nuxt module resolves its own layer roots.

See [endpoint organization](/handlers/organization) and [catalog inspection](/advanced/listing-definitions).
