## Infer input and output types

Use complete schemas, such as `z.object(...)`, for both inputs and outputs. The callback receives parsed inputs, including defaults, and its result must match the output schema:

```ts [server/mcp/tools/multiply.ts]
import { z } from 'zod'
import { defineMcpTool } from '@nuxtjs/mcp-toolkit/server'

export default defineMcpTool({
  description: 'Multiply a value by a factor',
  inputSchema: z.object({ value: z.number(), factor: z.number().default(2) }),
  outputSchema: z.object({ result: z.number() }),
  handler: ({ value, factor }) => ({ result: value * factor }),
})
```

`factor` is a number inside the handler. Returning a string for `result` fails type checking; returning invalid data at runtime also fails output validation. Return schema data directly. Use `toolResult()` for an explicit protocol envelope.

For an extracted schema, `z.input<typeof schema>` describes accepted values and `z.output<typeof schema>` describes parsed values. An explicit return annotation is useful when a callback returns enum literals:

```ts [server/mcp/tools/health.ts]
import { z } from 'zod'
import { defineMcpTool } from '@nuxtjs/mcp-toolkit/server'

const healthOutput = z.object({ status: z.enum(['ok', 'degraded']) })

export default defineMcpTool({
  description: 'Read service health',
  outputSchema: healthOutput,
  handler: (): z.input<typeof healthOutput> => ({ status: 'ok' }),
})
```

There is no empty input schema. The output schema still describes and validates the result.

## Type input examples

Check examples against the schema's input type so fields with defaults may be omitted:

```ts
import { z } from 'zod'

const searchInput = z.object({ query: z.string(), limit: z.number().default(10) })
const examples = [{ query: 'caching' }] satisfies z.input<typeof searchInput>[]
const documentedInput = searchInput.meta({ examples })
```

Use `documentedInput` as the tool's `inputSchema`. This is Zod 4 schema metadata, separate from MCP `_meta`; see [annotations and metadata](/tools/annotations).

## Use the inferred request event

A tool with inputs receives `(args, event)`. A tool without inputs receives `event` directly. The event is inferred as `McpEvent`, so a callback does not need a manual annotation:

```ts [server/mcp/tools/request-info.ts]
import { defineMcpTool } from '@nuxtjs/mcp-toolkit/server'

export default defineMcpTool({
  description: 'Read request information',
  handler: event => ({ userAgent: event.req.headers.get('user-agent') }),
})
```

`McpEvent` uses H3 v2 in both Nitro versions. Its context includes the current protocol request and endpoint notifier at `event.context.mcp.notifier`. Nitro 2 middleware context is preserved, but an API requiring a native H3 v1 event cannot accept this event unchanged. Keep application services independent of the event type where possible.

## Choose explicit imports or auto-imports

Nuxt auto-imports the following into server files by default:

- Definitions: `defineMcpTool`, `defineMcpResource`, `defineMcpPrompt`, `defineMcpPlugins`.
- Composition and results: `createMcpHandler`, `createMcpOAuth`, `toolResult`, `imageResult`, `audioResult`.
- Input requests: `inputRequired`, `mcpElicit`, `mcpElicitUrl`, `getElicitedContent`, `getInputResponses`, `getMissingInputs`, `canRequestInput`, `getSupportedInputs`, `defineRequestState`.
- Protocol errors: `McpJsonRpcError`.
- Types: `McpEvent`, `McpTool`, `McpResource`, `McpPrompt`, `McpHandler`, `McpHandlerOptions`.

All are also available through explicit imports from `@nuxtjs/mcp-toolkit/server`. Disable auto-imports with `mcp.autoImports: false`. Zod remains an application import.

The beta removes SDK-specific extras, session helpers, `useMcpServer()`, and the global catalog getters. Use the callback's event and the generated endpoint's `definitions` array instead. See the [migration guide](/getting-started/beta-migration) and [catalog example](/tools/groups-organization#read-the-generated-catalog).

## Check examples in your application

Run Nuxt's preparation step before checking a new app so module options and server auto-imports are generated. Then run your application's type checker. A documentation snippet does not replace the generated Nuxt context or the runtime validation of an incoming call.
